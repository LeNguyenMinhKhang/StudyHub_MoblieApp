# Query and ORM Optimization

Start with observed slow queries, timeouts, CPU, or connection pressure. Do not optimize by intuition alone.

## Query workflow

1. Find the exact SQL generated by the endpoint or background job.
2. Reproduce with representative parameters and data distribution.
3. Run `EXPLAIN (ANALYZE, BUFFERS)` in a safe environment; inspect row-estimate errors, scans, joins, sorts, and buffer reads.
4. Change one access pattern or index at a time and compare latency and resource use.
5. Recheck correctness, including RLS policy behavior.

`EXPLAIN ANALYZE` executes the statement. Avoid running it on a mutating query against production unless the effects are controlled.

## Spring Data/JPA checks

- Detect N+1 query patterns from SQL logs/APM. Use a projection, explicit fetch join, or entity graph for the particular use case.
- Avoid broad eager loading and huge fetch joins across multiple collections.
- Select only needed columns for read endpoints; paginate at the database.
- Batch writes where appropriate and keep batches bounded.
- Review generated SQL and bind values safely; never concatenate user input into SQL.
- Keep transactions short and do not hold them while making remote calls.

For Supabase, compare application latency with database query insights and plans. A slow request can be caused by pool waits, network round trips, RLS evaluation, or SQL execution; identify which layer is responsible.
